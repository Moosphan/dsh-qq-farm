## 0. 结论

**1. 基座选定：`rainnight6/qq-farm-copilot`（GPLv3）。**

理由不是"它 star 最多"（它只有 90★，`megumiss` 是 201★），而是三条硬证据：

| 证据 | 说明 |
|---|---|
| **它就是当前上游** | `490720818/qq-farm-copilot` → 301 重定向 → 仓库 id `1246804211` → 即 `rainnight6/qq-farm-copilot`。同一作者改号，README 里的"项目地址 490720818"指向自己 |
| **活跃度最高** | 最近 100 次提交跨 2026-05~10；作者含 `DESKTOP-KRBOUSV\49072`（490720818 本机）与 `Megumi`（原作者）。`megumiss` 主线 2026-06-12 后停更（6 月仅 1 次提交） |
| **功能最全** | 18 个任务模块、145 个按钮定义、294 张 QQ 模板、恢复阶梯完整 |

**2. 排除另外两个开源视觉项目**：`flh155/qq-farm-bot-vision`（MIT，但只有 2448 行、1 张模板、无调度无恢复、2026-04 停更）；`hacker-frok/qq-farm-bot-ai`（399★，功能最全，但**闭源**，只有 Windows x64 二进制，不可复用）。

**3. 协议方案按你的判断降级**：不投入，但 FAP 里预留 `platform: protocol` 的字段位，将来想接再实现，不改架构。

**4. "保质保量"的落点不是选对基座，而是补齐它的工程缺口。** 基座有 5 个真实短板：0 测试、单作者、微信支持依赖内存补丁、CPU 占用高、误识别无二次确认。我们在这之上加的 10 项工程化能力（§4）才是本项目的真正价值。

## 2. 基座代码实测（不是读 README，是读代码）

### 2.1 工程指标

| 指标 | 实测值 | 解读 |
|---|---|---|
| Python 文件数 | 82 | 分层清晰（platform / vision / ui / engine / tasks / models） |
| 类型标注（`->`） | 648 处 | 作者是有意识写类型注解的，`from __future__ import annotations` 全量使用 |
| pydantic BaseModel | 5 类 | 配置模型强类型化，不是裸 dict 满天飞 |
| `except:` 裸捕获 | **0** | 值得肯定的纪律 |
| `except Exception:` | 221 处 | 偏多，但配合 651 处结构化日志，属于"防御式"而非"掩盖式" |
| loguru 日志点 | 651 | 可观测性基础在 |
| 装饰器分派（`@DecoratorConfig`） | 12 | 用装饰器做"运行模式/平台"分派，比 if-else 干净 |
| 测试 / CI | **0 / 无** | ⚠️ 最大缺口 |

### 2.2 视觉层实现（决定识别质量的根）

```python
# core/vision/cv_detector.py 实测要点
cv2.matchTemplate(slot, template_image, cv2.TM_CCOEFF_NORMED)   # 归一化互相关
  ├─ 多尺度匹配（scale 遍历，支持 DPI/分辨率差异）
  ├─ alpha 通道 mask（透明按钮不污染匹配）
  ├─ 复合模板合成（_make_crop_composite_seed_template：种子 + 背景）
  ├─ NMS 去重（iou_threshold=0.5）
  └─ 分页级模板子集（detect_category 而非全量 145 个全扫）
```

**评价**：这是"能上生产"的视觉层写法。多尺度 + mask + NMS + 分类匹配这四件套，比 flh155 那种"固定阈值 0.4~0.65 硬编码"高一个层次。

**但仍有明显代价**：145 个模板 × 多尺度 × 每帧 → 这就是 issue 里 `[Suggestion]: 关于识别时CPU占用过高是否可以使用GPU？` 的来源。

### 2.3 平台层（决定"后台 + 多开"能否成立）

| 能力 | 实现 | 成熟度评价 |
|---|---|---|
| 后台截图 | `PrintWindow(PW_RENDERFULLCONTENT)` → 失败退回 0 | ✅ 已验证；有 `_record_print_failure` 连续失败阈值，区分"偶发黑帧"与"真挂了" |
| 后台点击 | `SendMessage(WM_MOUSEMOVE/LBUTTONDOWN/UP)` + 客户区坐标换算 | ✅ 已验证（见 §5 关于 Chromium 的辨析） |
| 防抢焦点 | `m.dll`：`WH_CBT` 拦 `HCBT_ACTIVATE/SETFOCUS` + `WH_CALLWNDPROC` 做子类化 | ✅ 巧思，40 行 C 解决大问题 |
| 微信后台 | `wechat_mouse_guard.py` 对 `wechatappex.exe` 做**内存补丁**（RVA `0x1450`/`0x14D8`） | ⚠️ **版本脆弱**：微信一升级 RVA 就变，必须做版本表 |
| 多实例 | `mp.Process` + 命令/事件双 `Queue` | ✅ 进程级隔离，崩溃不传染 |

### 2.4 业务层

- 18 个任务模块，`_run_task_*` 自动发现 + 统一调度器（`interval`/`daily`，`next_run` 持久化，`task_order` 定序）；
- 恢复阶梯：`repair`（≤3 次）→ 重启窗口 → 停机 + 通知；
- 地块巡查 → OCR 采倒计时 → `timed_harvest` 按聚合时间生成执行点（这条链路是"智能挂机"的核心，别人没有）。

## 3. Issue 暴露的真实故障模式（最有价值的一手情报）

我把上游 issue 按"现象 → 根因 → 我们怎么根治"整理成表。**这些就是"保质保量"要对付的清单**：

| # | 用户报的现象（真实 issue） | 根因 | 我们的根治手段 |
|---|---|---|---|
| 1 | 「频繁出现长时间无操作提示」 | 卡死判定阈值一刀切，长任务被误判 | 分任务超时表 + 状态机可视化（面板能看到"卡在哪一步"） |
| 2 | 「最新活动的四格农作物不会采摘」 | 业务未实现（四格收益低，作者主动不做） | 保持同样取舍，但**在面板显式标注"不支持四格"**，避免用户误解 |
| 3 | 「好友偷菜标不显示，要重启农场才刷新」 | **游戏客户端 UI 不刷新**（不是 bot 的 bug） | Agent 侧加"客户端卫生"：会话超时软重启窗口 + UI 刷新探测 |
| 4 | 「错误识别空地，导致异常购买种子」 | 视觉误判 + 动作无二次确认 | **动作前双确认**（模板 + 区域颜色 + OCR 三点一致）+ 单日购买预算上限 |
| 5 | 「微信后台模式还是抢鼠标」 | `wechatappex` 内存补丁失效（版本不符） | 微信版本探测 → 补丁表匹配 → 不匹配则**自动降级前台模式并明确提示**，不静默乱点 |
| 6 | 「识别时 CPU 占用过高，能用 GPU 吗」 | 145 模板 × 多尺度 × 每帧 | ROI 区域裁剪 + 页面级模板子集 + 空闲降帧 + 可选 onnxruntime GPU |
| 7 | 「等级识别运行时不自动更新」 | 缓存/回写时机问题 | 每轮强制采样 + 置信度校验 + 面板显示"上次同步时间" |
| 8 | 「win11 启动一直在上面点击，识别不了」 | 首帧未稳定就开始动作 | 启动收敛阶段（等待画面稳定 N 帧）才允许点击 |
| 9 | 「会导致屏幕锁帧吗」 | 后台截图 + 高频匹配占用 GPU 合成 | 截图频率可配 + 降帧策略 |
| 10 | 「兼容 macOS」×3 | 平台层缺失 | **我们的主攻方向** |

> 注意 #3 和 #5：这两个不是"写得好就能解决"的，是**外部依赖问题**。工程化方案必须是"探测 + 降级 + 明确告知"，而不是假装能修。

## 5. 一个必须澄清的技术辨析：Chromium 到底吃不吃 PostMessage？

Cua 的 Windows 逆向文章里有句话：

> "`PostMessage` keeps the user's desktop alone, **then Chromium content ignores those clicks**."

而参考项目用 `SendMessage` 投递点击，实测是**有效的**。矛盾吗？不矛盾，原因是目标不同：

| 目标 | 是否吃合成鼠标消息 | 原因 |
|---|---|---|
| Chrome 自身的标签页内容 | ❌ 丢弃 | Chrome 在 renderer IPC 边界做了用户手势白名单校验 |
| CEF 内嵌应用（微信/QQ 小程序宿主） | ✅ 接受 | CEF 的宿主窗口就是 `Chrome_WidgetWin_0` 本体，`SendMessage` 直接进它的窗口过程，不走 Chrome 那套校验 |

**这解释了为什么参考项目能成立、也解释了为什么它"只对小程序窗口有效"。** 同时也告诉我们：这条路是**目标特化**的，一旦腾讯换了小程序宿主实现（例如换成别的 WebView 内核），`SendMessage` 可能一夜失效 —— 这是 D2 风险的真实形态，缓解手段是**保留 WGC（Windows.Graphics.Capture）+ UIA 作为第二通道**，并做能力探测。

## 7. 与上游的关系：fork 还是嵌入？

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **嵌入不改**（把我方 Agent 包在它外面，只调 3 个入口） | 升级容易、许可清晰、改动最小 | 受制于它的 API 与 bug 节奏 | **M1 采用** |
| **Fork 后裁剪**（拿掉 GUI，改成受控引擎） | 能修 bug、能加 Q1~Q10 | 需要持续跟上游、维护成本高 | **M2 之后视缺口决定** |
| 完全重写 | 最干净 | 22k 行 + 294 模板，不现实 | 不采用 |

**建议路径**：M1 嵌入 → 用 Q1/Q2 建起"可观测"→ 若上游停更或关键 bug 不修，再 fork 接盘（此时我们已有回归集，接盘成本低）。**先建回归集再决定 fork，顺序不能反。**
