# dsh-qq-farm 技术方案（v0.1 草案）

> DeepSeek Harness 插件：QQ 经典农场自动化助手面板
> 目标平台：Windows + macOS（插件侧平台无关，自动化侧按平台实现）
> 参考实现：[rainnight6/qq-farm-copilot](https://github.com/rainnight6/qq-farm-copilot)（GPLv3）
> 状态：方案评审中，未开工

---

## 0. 结论摘要（TL;DR）

**可行性结论：可行，但要接受"三层拆分"，不能做成"一个插件包打天下"。**

| 判断 | 结论 | 理由 |
|---|---|---|
| DSH 插件形态（面板 + 宿主能力） | ✅ 确定可行 | 树外插件有成熟范式（你机器上的 `dsh-opencode-palette` 就是），宿主半可注册 HTTP/WS 路由、settings、LLM 工具；浏览器半有 `slots` 插槽位 |
| 插件在 macOS 上跑 | ✅ 确定可行 | 面板/控制面/协议层与游戏无关，纯 Node + React，天然跨平台 |
| 在 macOS 上**直接**自动化游戏 | ⚠️ 部分可行，风险中高 | 游戏本身有 Mac 版（微信/QQ 桌面版小程序），但 macOS 平台层要全新自研：窗口后台截图、无焦点输入、多开窗口管理的可行性**未验证**，需要 POC |
| 在 Windows 上自动化游戏 | ✅ 有现成路基 | 参考项目已跑通：`PrintWindow` 后台截图 + `SendMessage` 后台点击 + `m.dll` 防抢焦点 + OpenCV + RapidOCR |
| 多开 + 后台运行 | ✅ Windows 可行；⚠️ macOS 待验证 | Windows 侧后台点击是消息级投递，天然支持多窗口并行；macOS 的等价能力（`CGEventPostToPid`）是否被小程序 WebView 接受需实测 |
| 复用参考项目代码 | ⚠️ 可行但有许可代价 | GPLv3：直接链接/衍生必须整包 GPLv3 开源；只能通过"独立进程 + IPC"做隔离边界 |

**推荐架构一句话**：`DSH 插件（跨平台控制面 + 面板）` ⇄ `Farm Agent 协议（本地/局域网）` ⇄ `平台 Agent（Win 复用参考项目内核 / macOS 自研平台层 / Mock 模拟器）`。

**关键取舍**：调度、截图、识别、点击全部下沉到 Agent；插件只做控制面、面板、LLM 工具。这样 DSH 重启/换前端不影响农场运行，也让"跨机器"成为自然延伸而不是补丁。

## 1. 需求与范围

### 1.1 明确需求（来自你的确认）

1. 交付物：DSH 插件 `dsh-qq-farm`，在工作台里显示为**自动化农场助手面板**。
2. 平台：支持 PC 端 QQ 与 PC 微信两个平台；支持多开、后台运行。
3. 运行环境：**不限于环境**，Windows 与 macOS 都要能跑起来。
4. 功能点可对齐参考项目（收获、播种、施肥、偷菜、帮忙、扩建、升级、奖励、商城、活动、统计等）。
5. 需要 LLM 工具接入：`farm_status` / `farm_run_task` / `farm_instances` 一类对话式操作。
6. 面板功能范围（全选）：实例总览 + 实时截图、运行控制、任务与调度配置、日志事件流、数据统计、地块地图、异常通知。

### 1.2 非目标（本方案明确不做）

- 不注入游戏进程、不做内存修改、不做协议破解/抓包重放（技术路线选择：只做**视觉 + 输入**，与参考项目一致，也降低封号与法律风险）。
- 不提供云托管；Agent 只监听本机回环，跨机需用户显式开启并配置鉴权。
- 不做"一键刷满/批量养号"类能力（与游戏条款冲突更严重，且违背最小必要原则）。

### 1.3 安全与合规基线（写进产品与文档）

- 自动化操作可能违反游戏服务条款，**账号风险由使用者承担**；首次启用需要显式二次确认。
- 默认只绑定 `127.0.0.1`；跨机模式必须带 token，且禁止默认开启。
- 插件默认以"只读观察"启动（不自动点开始），避免装载即动鼠标。

## 2. 参考项目拆解（qq-farm-copilot）

### 2.1 技术底座

| 层 | 实现 | 关键依赖 |
|---|---|---|
| 窗口管理 | Win32 枚举/选择/调整窗口、多屏、虚拟桌面 | `pywin32`、`pygetwindow`、`pyvda` |
| 截图 | 前台 `mss` 区域截图 / 后台 `PrintWindow(PW_RENDERFULLCONTENT)` | `mss`、`ctypes` |
| 输入 | 后台 `SendMessage(WM_MOUSEMOVE/LBUTTONDOWN/UP)`；前台 `mouse_event` | `pywin32` |
| 防抢焦点 | 自编译 `m.dll`：`WH_CBT` 钩子拦 `HCBT_ACTIVATE/SETFOCUS` + `WH_CALLWNDPROC` 做窗口子类化 | C / MSVC |
| 视觉 | OpenCV 模板匹配（`cv2.matchTemplate`），模板分 `templates/qq` 与 `templates/wechat` | `opencv-python` |
| OCR | 等级、地块倒计时、仓库种子数字块 | `rapidocr` + `onnxruntime` |
| 引擎 | `BotEngine`（代理）+ `BotWorker`（`multiprocessing` 子进程）+ `TaskExecutor`（单线程串行调度） | PyQt6（QtCore 事件循环 + signal） |
| 任务 | `_run_task_<name>` 自动发现，`interval` / `daily` 两种触发 | — |
| 配置 | 每实例 `configs/config.json`（`tasks` 为动态字典，持久化 `next_run`） | `pydantic` |

规模：约 **2.2 万行 Python**，其中 `executor.py`(1347)、`runtime.py`(1347)、`window_manager.py`(1484)、`cv_detector.py`(821)、`main_planting.py`(931)、`land_scan.py`(1141)、`friend.py`(1157)。

### 2.2 功能清单（可直接映射为我们的需求池）

| 类别 | 功能 | 备注 |
|---|---|---|
| 主流程 | 一键收获 / 务农 / 自动买种 / 自动播种 / 施肥（按剩余成熟时间）/ 扩建 / 升级 | 四格种子明确不支持 |
| 仓库 | 批量出售 | |
| 领取 | 任务奖励、分享奖励（仅微信）、商城免费、QQSVIP 礼包、邮件、月卡 | 分项开关 |
| 好友 | 偷菜（时段 + 次数上限 + 黑名单）、帮忙（仅护主犬模式可选）、好友申请 | 偷菜统计需 OCR，会变慢 |
| 地块 | 地块巡查（滑动分段 + 逐格 OCR）、定时收获（按聚合时间生成执行点）、自动种草 | 巡查结果是定时收获的前置 |
| 活动 | 通用活动资源依次领取，到时自动关闭 | 每次活动都要适配模板 |
| 运维 | 定时重启窗口、异常自动重启/一键修复、异常通知（Windows Toast / OnePush）、截图与日志留存 | 恢复策略 `prefer_repair_before_restart` |
| 统计 | 按天累计 `harvest/operation/friend_steal/friend_help` → CSV | 我们在面板里改成实时图表 |

### 2.3 可直接借鉴的"稳定性设计"（这部分比功能更值钱）

1. **进程隔离**：Bot 跑在 `multiprocessing` 子进程，主进程 GUI 不卡，崩溃可重启。
2. **异常恢复分级**：任务异常 → 重启窗口重试 N 次 → 一键修复（最多 3 次）→ 重启任务 → 停机 + 通知。
3. **卡死判定**：`stuck_seconds`(60) / `stuck_long_wait_seconds`(120) 无有效点击即判定卡死。
4. **截图失败阈值**：`PrintWindow` 连续失败计数达阈值即抛异常触发上层恢复（区分"偶发黑帧"与"真挂了"）。
5. **点击节流 + 随机抖动**：`interval >= 1`、随机坐标偏移、随机延时、单轮点击上限。
6. **状态对账**：页面识别（`ui_get_current_page`）→ 未知页先清弹窗 → 兜底回主页。
7. **持久化 `next_run`**：重启后调度不丢。
8. **幂等收敛**："点击 ≠ 到达"，跳转流程以"页面已到达"为结束条件。

> 这 8 条要作为我们 Agent 侧的**硬性设计约束**照搬，因为农场自动化的失败模式 80% 来自这几点。

### 2.4 许可证

**GPLv3**。影响见 §11：Agent 半必须以 GPLv3 开源；DSH 插件半（不含派生代码）可以独立许可，但要守住"进程边界 + 无共享数据结构"这条线。

## 3. 总体架构

### 3.1 三层拆分

```
┌───────────────────────────────────────────────────────────────┐
│  DSH 工作台（浏览器 / macOS / Windows 均可）                    │
│  ┌─────────────────────────────────────────────────────────┐  │
│  │ dsh-qq-farm 浏览器半（预构建 ESM bundle，React）          │  │
│  │  · 实例总览/截图预览  · 运行控制  · 任务与调度配置          │  │
│  │  · 日志事件流  · 统计图表  · 地块地图  · 异常通知           │  │
│  └──────────────────────────┬──────────────────────────────┘  │
│                             │ fetch / WebSocket（同源）        │
│  ┌──────────────────────────┴──────────────────────────────┐  │
│  │ dsh-qq-farm 宿主半（cordis 插件，Node 进程内）             │  │
│  │  · /plugins/dsh-qq-farm/* REST + WS 网关                 │  │
│  │  · Agent 连接池（多机/多实例）、自动重连、状态缓存           │  │
│  │  · ctx.settings 配置命名空间                             │  │
│  │  · ctx.tools：farm_status / farm_run_task / farm_instances │  │
│  │  · 进程托管（同机 Agent 的拉起/重启/日志收集）              │  │
│  └──────────────────────────┬──────────────────────────────┘  │
└─────────────────────────────┼─────────────────────────────────┘
                              │ Farm Agent Protocol（HTTP + WS）
              ┌───────────────┴────────────────┐
              │                                │
┌─────────────┴──────────────┐   ┌─────────────┴──────────────┐
│  Farm Agent (Windows)      │   │  Farm Agent (macOS)        │
│  · 复用参考项目内核(嵌入)    │   │  · 自研平台层（M3 目标）    │
│  · 定时调度/恢复/截图/识别    │   │  · ScreenCaptureKit 截图    │
│  · 多实例（每实例=一个窗口） │   │  · CGEventPostToPid 输入    │
│  · 本地持久化                │   │  · Vision OCR              │
└────────────────────────────┘   └────────────────────────────┘
              │
┌─────────────┴──────────────┐
│  Farm Agent (Mock)         │  ← 任意 OS，合成截图 + 假状态机
└────────────────────────────┘
```

### 3.2 为什么必须这样拆（而不是插件里直接调 Python）

1. **DSH 是"Web GUI + Node 宿主"**：面板跑在浏览器里，浏览器没有任何访问 Win32/macOS 图形栈的能力。任何真实操作都必须发生在宿主操作系统上的一个进程里。
2. **平台无关性要求**：插件代码一旦写进 `user32.SendMessage`，就永远只能 Windows。反过来把平台能力关进 Agent，插件就天然跨平台，且 Mac 只需接一个不同的 Agent，面板零改动。
3. **稳定性**：农场是长时任务（数小时~数天）。DSH 会话会被关闭、页面会刷新、`dsh web` 会重启。调度放在 Agent，DSH 重启只是"换个遥控器"。
4. **多开**：每个实例一个窗口一个会话，天然多进程/多线程并行，不共享全局输入状态。
5. **工程隔离**：GPL 代码只存在于 Agent 侧，许可边界清晰。

### 3.3 三种部署拓扑（同一套代码全支持）

| 拓扑 | 场景 | Agent 位置 | 插件配置 |
|---|---|---|---|
| **T1 同机（Windows）** | DSH 和 QQ/微信 都在 Windows 上 | 插件托管子进程，`127.0.0.1` | `agent.mode: "managed"` |
| **T2 同机（macOS）** | DSH 和 QQ/微信 都在 Mac 上 | 插件托管子进程，`127.0.0.1` | `agent.mode: "managed"` |
| **T3 跨机** | DSH 在 Mac（或笔记本），游戏在 Windows 台式机 | 独立服务，局域网 | `agent.mode: "remote"` + `url` + `token` |

**T3 是"Mac 上也能用"的兜底方案**，且实现成本极低（协议一致，只是换 host）。建议一开始就让 Agent 的监听地址/token 可配置，别写死 localhost。

## 4. DSH 插件技术方案

### 4.1 插件包结构

```
dsh-qq-farm/
├─ package.json          # dsh.bundle.patch + dsh.client.{platform,inject}
├─ cordis.patch.yml      # bundle 层：insert { id: qq-farm, name: 'dsh-qq-farm', config: {...} }
├─ lib/
│  ├─ index.js           # 宿主半（cordis 插件，手写 ESM，无构建）
│  ├─ client.js          # 浏览器半（esbuild 产物，勿手改）
│  ├─ routes.js          # REST/WS 网关
│  ├─ agent-client.js    # FAP 客户端 + 连接池 + 重连
│  ├─ supervisor.js      # 同机 Agent 进程托管
│  └─ tools.js           # LLM 工具定义
├─ shared/
│  └─ fap-types.js       # 协议常量与校验（宿主/浏览器/agent 三方共用）
├─ agent/                # 独立发布单元（GPLv3）
│  ├─ win/               # Windows 后端（嵌入参考项目内核）
│  ├─ mac/               # macOS 后端（M3）
│  └─ mock/              # 模拟器
└─ web/                  # 面板源码（TSX）→ esbuild → lib/client.js
```

**技术事实（已核实）**：
- 树外插件用 `dsh plugin --profile web add <pkg>` 安装（内部转发 pnpm）。
- 宿主半就是普通 cordis 插件：`export const name` + `export function apply(ctx)`。
- 浏览器半是**预构建 bundle**，用 `window.__ModuleLoader__.load({ id, factory })` 注册；factory 内部可以 `require('react')`（平台种子词），也可以 `ctx.get('slots')`。
- `dsh-client-hmr` 会轮询 bundle 哈希，本地重建 `client.js` 即自动热重载 —— **开发循环很舒服**，不需要重启 DSH。
- 浏览器半必须**自包含**：不要把 React 或 DSH 内部包打进去（破坏纯度门禁 / 版本漂移）。

### 4.2 宿主半能力清单

| 能力 | 用法 | 说明 |
|---|---|---|
| HTTP 路由 | `ctx.webServer.register({ kind: 'prefix', path: '/plugins/dsh-qq-farm', handler })` | REST：实例列表、配置读写、控制命令、日志分页、统计 |
| WS 上行/下行 | `ctx.webServer.registerUpgrade({ path: '/plugins/dsh-qq-farm/stream', handler })` | 截图帧（二进制）+ 事件（JSON）单连接复用 |
| 配置持久化 | `ctx.settings.register('qq-farm', schema, { base })` | 配置进 DSH 设置文档，用户可读可改；切换 profile 不丢 |
| LLM 工具 | `ctx.tools.register({ name, description, parameters, execute })` | 见 §4.5 |
| 子进程 | `ctx.subprocess.spawn(...)`（或 Node `child_process`） | 同机 Agent 托管；采集 stdout 做日志 |
| 生命周期 | `ctx.effect(() => dispose)` / `ctx.on('dispose')` | 插件卸载时断开 WS、终止托管进程 |

> 安全注意：`/plugins/**` 路由**不走** `/api` 的 loopback 信任栅栏（那套只护 `/api`）。因此我们自己的路由必须自己做：① 只接受同源（校验 `Origin`/`Sec-Fetch-Site`）；② 写操作要求 `X-QQFarm-Action-Token`（插件启动时随机生成，注入进 boot manifest 或首帧下发）；③ 跨机模式必须显式开启 + token 校验。**这一条是设计红线**：面板能点"开始"，等于能控制鼠标键盘。

### 4.3 浏览器半：面板落位

已核实的可用插槽（`SlotMap`）：

| 插槽 | 类型 | 用途 |
|---|---|---|
| `conversation.view` | list / session | **主面板**：作为会话标签页（与 Chat / Trajectory 并列） |
| `conversation.session.header.utilities` | list / session | 顶栏开关按钮（带运行状态徽标） |
| `shell.overlay` | list / root | **悬浮状态胶囊**：任何页面都可见的"3 实例运行中 / 1 异常" |
| `settings.section` | list / root | 设置页一级入口（Agent 连接、快捷键、风险确认、高级参数） |
| `sidebar.footer.action` | list / root | 侧栏 footer 快捷入口（可选） |

**推荐的注册方式**（沿用已验证的 declaration-injection 写法）：

```js
exports.inject = ['slots']
exports.apply = (ctx) => {
  const slots = ctx.get('slots')
  ctx.effect(() => slots.inject('conversation.view', () => slots.register({
    name: 'conversation.view',
    id: 'qq-farm',
    order: 20,
    label: () => '农场',
    inject: farmApi,          // 我们自己构造的 API 面（订阅/命令）
  }, FarmDashboard)))
  // 同理注入 shell.overlay / settings.section / header.utilities
}
```

**降级策略**：`conversation.view` 是内部契约，跨 DSH 版本有变动风险（见 §9 D7）。因此面板核心同时按"可用插槽探测"装配：`conversation.view` 不可用就退到 `shell.overlay` 悬浮窗，再不可用就在 `settings.section` 里给完整页面。**绝不让面板因为插槽缺失而白屏。**

### 4.4 面板信息架构

```
┌─ 农场面板 ─────────────────────────────────────────────────┐
│ [实例栏]        │  [主区]                                    │
│ ● 账号A QQ     │  ┌ 实时画面（WebP, 自适应缩放, 点击测坐标）┐ │
│   运行 / 任务: │  │                                          │ │
│   friend 18s   │  └──────────────────────────────────────────┘ │
│ ○ 账号B 微信   │  [开始][暂停][停止][立即执行][截图][修复][重启] │ │
│   已暂停       │  ┌ 状态卡：等级/金币/点券/经验/今日收获 ────┐ │
│ ⚠ 账号C 异常   │  └──────────────────────────────────────────┘ │
│                │  ┌ 地块地图 6×4 ────────────────────────────┐ │
│ [+ 新增][克隆] │  │ 每格：等级色/倒计时/需播种/需升级徽标       │ │
│                │  └──────────────────────────────────────────┘ │
│                │  ┌ Tabs: 任务调度 | 日志 | 统计 | 设置 ─────┐ │
│                │  └──────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────┘
```

- **实时画面**：Agent 侧 1 fps（面板不可见时 0.2 fps / 完全停）、可见时 4~6 fps；JPEG/WebP q60，720p 上限，单帧 < 120 KB；面板内做"最新帧覆盖"策略（丢旧帧，不排队）。
- **地块地图**：直接吃 `land_scan` 的结果（`plot_id / level / maturity_countdown / countdown_sync_time / need_planting / need_upgrade`），前端按 `countdown_sync_time` 本地插值倒计时，不依赖 Agent 高频推送。
- **日志**：Agent 结构化日志（`ts, level, instance, task, page, action, coord, confidence, result`），WS 增量 + REST 分页回捞；卡片里可展开"点击动作回放"（动作前帧 + 坐标框）。
- **统计**：`daily_action_stats` 改成 Agent 侧结构化存储，前端画 7/30 天柱状图。
- **异常通知**：面板内 Toast + 徽标；外部推送（Windows Toast / 企业微信 / OnePush）在 Agent 侧实现，插件只做开关。

### 4.5 LLM 工具（DSH 相对原桌面程序的核心增量）

```text
farm_instances()                      → 实例清单与健康摘要（不需要真实点击，只读）
farm_status(instance_id)              → 等级/金币/地块状态/当前任务/下次执行/最近异常
farm_run_task(instance_id, task)      → 立即执行某任务（白名单：harvest/sell/reward/...）
farm_control(instance_id, action)     → start|pause|resume|stop|screenshot
farm_logs(instance_id, since, level)  → 日志切片（给模型做根因分析）
```

设计约束：
- **只读优先**：`farm_status/instances/logs` 默认允许；`farm_run_task/farm_control` 走 DSH 的 `ctx.tools.guard` 或参数确认，避免模型误触"停止全部"。
- **有界输出**：截图以"URL + 摘要"返回，不把 PNG 塞进会话（会吃爆 context）；需要看图时让模型显式调 `farm_screenshot`。
- **错误可解释**：Agent 返回结构化错误码（`E_WINDOW_LOST` / `E_PAGE_UNKNOWN` / `E_STUCK` / `E_TEMPLATE_MISS`），模型据此给出"去把窗口拉出来"这类可执行建议。

## 5. Farm Agent Protocol（FAP）

### 5.1 设计原则

1. **控制面/数据面分离**：命令走 REST（可重试、可幂等、可鉴权），状态与帧走 WS（可丢、可合流）。
2. **Agent 是真相源**：调度、配置、持久化都在 Agent；插件是控制面 + 缓存。DSH 重启不中断农场。
3. **向后兼容**：`version` 协商；未知字段忽略；未知方法返回 `E_UNSUPPORTED` 而非断开。
4. **失败有语义**：每个错误都有稳定错误码，面板与 LLM 都能据此决策。

### 5.2 端点

```text
GET    /v1/health                     → { agent, version, platforms, instances }
GET    /v1/instances                  → [InstanceSummary]
POST   /v1/instances                  → 创建（platform: qq|wechat, window 选择规则）
DELETE /v1/instances/:id
POST   /v1/instances/:id/clone
PATCH  /v1/instances/:id              → 重命名/改配置（含 tasks.*）
GET    /v1/instances/:id/state        → 全量状态快照（含 land.plots、profile）
GET    /v1/instances/:id/screenshot   → image/webp（单帧）
GET    /v1/instances/:id/logs?since&limit&level
GET    /v1/instances/:id/stats?from&to
POST   /v1/instances/:id/control      → { action: start|pause|resume|stop|run_once|repair|restart }
POST   /v1/instances/:id/task         → { task: "friend" } 立即触发
GET    /v1/instances/:id/config       → 实例配置
PUT    /v1/instances/:id/config       → 整份/差量（带 revision 冲突检测）
WS     /v1/stream                     → 事件 + 帧
```

### 5.3 WS 消息

```jsonc
// 上行（Agent → 插件）
{ "t": "hello",   "version": "1.0", "agent": "win", "versionId": 12 }
{ "t": "state",   "instance": "a1", "rev": 87, "patch": { /* JSON-Patch 子集 */ } }
{ "t": "log",     "instance": "a1", "entries": [{ "ts": 1730000000, "level": "info", "task": "friend", "msg": "点击", "action": "btn_harvest", "x": 312, "y": 880, "conf": 0.94 }] }
{ "t": "event",   "instance": "a1", "kind": "task_start|task_end|recover|stuck|error", "detail": {…} }
{ "t": "frame",   "instance": "a1", "seq": 9912, "ts": …, "mime": "image/webp", "data": "<base64>" }
{ "t": "ack",     "id": "cmd-7", "ok": true, "result": {…} }   // 命令回执（也可用 REST 返回）

// 下行（插件 → Agent）
{ "t": "subscribe",  "instances": ["a1"], "frames": { "a1": { "fps": 4, "maxW": 720 } } }
{ "t": "unsubscribe" }
{ "t": "ping" }
```

### 5.4 幂等与背压

- 所有 `control` 命令带 `idempotencyKey`；Agent 保留 30 秒去重窗口。
- 帧**永不排队**：发送队列长度 1，新帧覆盖旧帧；面板不可见时插件主动降 fps（省 CPU 与带宽）。
- 日志走批量（200 ms 或 32 条聚合），断线期间 Agent 保留环形缓冲（默认 5000 条/实例），重连后按 `since` 补齐。
- 状态用 patch + `rev` 序列号；插件发现 `rev` 跳号即拉一次全量快照（自愈）。

### 5.5 鉴权

- 默认：`127.0.0.1` + 每次启动生成的 `agentToken`（写进 Agent 的 `~/.dsh-farm/agent.json`，权限 0600）。
- 跨机：必须 `--bind 0.0.0.0 --token <长随机>`，且建议用户走 SSH 隧道；面板里对"跨机模式"给出明确风险提示。

## 6. 平台后端

### 6.1 Windows 后端（M1 目标：功能对等）

**策略：嵌入参考项目内核，加一层薄适配（Adapter），不改其业务代码。**

技术可行性（已确认）：`core/` 与 `tasks/` 只依赖 PyQt6 的 **QtCore**（`QObject`/`pyqtSignal`/`QTimer`/`QEventLoop`），不依赖 GUI 部件。因此可以：

```python
# agent/win/engine_adapter.py（示意）
os.environ["QT_QPA_PLATFORM"] = "offscreen"
app = QCoreApplication([])          # 无 GUI 的 Qt 事件循环
bot = BotEngine()                    # 参考项目现成入口，信号接我们的回调
bot.signal_stats.connect(lambda s: hub.publish_state(s))
bot.signal_preview.connect(lambda img: hub.publish_frame(img))
hub.on_control("start", lambda: bot.start_instance(...))
```

需要处理的适配点（这些就是 M1 的主要工作量）：

| 适配点 | 现状 | 我们要做的 |
|---|---|---|
| Qt 事件循环 | 参考项目在 GUI 主线程跑 | 换成 `QCoreApplication` + `offscreen`，agent 进程独立 |
| 预览帧 | 通过 signal 推给 Qt 控件 | 接住后编码 WebP，推 FAP |
| 配置路径 | `%APPDATA%\QQFarmCopilot\instances\<id>` | 改为 `QFARM_HOME` 可配置，避免与国内原版共存冲突 |
| 日志 | `loguru` 写文件 | 加 stdout 结构化 + 环形缓冲 |
| 窗口选择 | 交互式 UI 里选 | 改为配置 + 自动匹配 + 失败上报（不能弹 UI） |
| 通知 | `winotify` / onepush | 保留，改为可选 |
| 模板目录 | 仓库内 `templates/` | 作为**外部数据目录**随包分发，支持用户更新（活动适配） |

**风险**：这把锁死在参考项目的内部 API 与节奏上（它一改 `BotEngine` 签名我们就得跟）。缓解：
- 适配层只依赖 3 个入口（构造、start/stop/pause、signal 集合），其余通过它自己的 `config.json` 走；
- 固定 pin 一个 commit，上游更新时做"回归用例 + 手动升级"，而不是自动跟随。

### 6.2 macOS 后端（M3，需先 POC）

游戏在 Mac 上是**微信/QQ 桌面版小程序**（[报道](https://it.ithome.com/archiver/0/934/172.htm)），所以"有窗口可截"没问题；难点全在**后台截图 + 无焦点输入 + 多开**。

| 能力 | macOS 手段 | 可行性判断 | 备注 |
|---|---|---|---|
| 窗口枚举 | `CGWindowListCopyWindowInfo` | ✅ 成熟 | 可拿到窗口 ID/所属进程/层级 |
| 窗口截图 | ScreenCaptureKit（14+）/ `CGWindowListCreateImage`（已废弃但可用） | ✅ 基本可行 | 需屏幕录制权限；**窗口被遮挡可截，最小化不可截** |
| 无焦点输入 | `CGEventPostToPid(pid, ev)` | ⚠️ **必须 POC** | 对原生 App 多数可用；对 CEF/WebView 是否被接受未知。被拒则退化 |
| 退化方案 | 系统级 `CGEventPost` + 置前 | ⚠️ 牺牲"后台" | 单账号尚可；多开切窗口时会有可见的焦点抖动 |
| OCR | Apple Vision `VNRecognizeTextRequest` | ✅ 很强，免费，无需模型 | 中文识别质量好于 RapidOCR，尺寸更小 |
| 模板匹配 | `opencv-python`（Mac 有轮子） | ✅ 可行 | 或走 Vision 的结构化识别减少模板依赖 |
| 防抢焦点 | 无 `m.dll` 等价物 | ❌ 不存在 | 这是 macOS 后台多开的**根本限制** |
| 多开 | 多个微信/QQ 实例（需用户自备多开方案） | ⚠️ 取决于用户环境 | 小程序窗口与账号绑定 |

**结论（建议）**：
1. **M0 先做 POC 脚本**（半天）：`CGEventPostToPid` 对微信小程序窗口点一个能识别的按钮，看有没有反应。这一步的结论直接决定 macOS 是"后台可用"还是"只能前台"。
2. 若 POC 通过 → M3 做完整 macOS 后端；若不通 → macOS 定位为 **T3 控制台**（连 Windows Agent），并在文档里讲清楚。
3. 无论哪种，macOS 都要**明确的"前台模式"**（窗口可见、接受焦点抖动），因为这是最稳的路径。

### 6.3 Mock 后端（M0，必须做）

- 合成截图（用参考项目的模板拼出"主页/好友页/地块弹窗"）+ 假状态机；

- 也是 CI 里唯一能自动跑的端到端路径（Windows GUI 自动化在 CI 里几乎不可行）。

## 8. 稳定性设计（重点章节）

### 8.1 分层监督（谁挂了谁来救）

```
DSH 宿主半  ──(supervise)──▶  Agent 进程  ──(supervise)──▶  实例 Worker  ──▶ 任务
   │                              │                            │
   │ 断开/崩溃 → 3s/6s/12s 退避重连 │ 退出码非 0 → 重启（限速）    │ 任务异常 → 修复→重启窗口→停机
   └─ 插件卸载 → 停止托管进程        └─ 优雅退出: SIGTERM, 5s 后 SIGKILL
```

### 8.2 必须实现的 8 条硬约束（照搬参考项目）

1. 实例之间**零共享状态**（独立 Worker、独立配置、独立窗口）；
2. 每条点击/识别都带**上下文日志**（任务/页面/按钮/坐标/置信度），否则线上问题无法复现；
3. 卡死判定（60s/120s 无有效动作）→ 触发恢复；
4. 截图连续失败阈值 → 判定"窗口真的没了"，而不是"这一帧黑"；
5. 跳转流程以"页面已到达"为结束，不以"点到了"为结束；
6. 恢复动作分级：重试 → 一键修复 → 重启窗口 → 停机通知（不无限重启）；
7. `next_run` 持久化，重启后调度不丢；
8. 所有控制命令**幂等**，重复下发不产生二次点击。

### 8.3 观测性

- **结构化日志**：`{ts, level, instance, task, step, page, action, x, y, conf, duration_ms, result}`；
- **指标**：任务成功/失败率、点击成功率、识别置信度 P50/P95、单轮耗时、恢复次数；
- **可回放**：每个 `action` 保存"动作前帧"（环形缓冲，默认 200 帧/实例，落盘可选），面板可逐帧回放——这是定位"为什么它点歪了"的唯一有效手段；
- **健康自检**：插件面板顶部显示 `Agent 连接 / 窗口在手 / 最后成功动作距今`，三个都绿才算"真的在跑"。

### 8.4 测试策略

| 层级 | 手段 |
|---|---|
| 协议层 | 纯 Node 单测 + 契约测试（插件 ↔ Mock Agent） |
| 面板层 | React Testing Library（DSH 自带这套）+ 快照 |
| 识别层 | **帧数据集回归**：录一段真实操作帧序列（含主页/地块/弹窗/异常），离线跑检测器，比对命中率与置信度分布 |
| 调度层 | Mock 时钟驱动的单测（不 sleep） |
| 端到端 | Mock Agent 全链路；Windows 真机人工冒烟（清单化） |

## 11. 许可证与合规

### 11.1 GPLv3 分析（必须提前定）

| 方案 | 是否衍生 | 结论 |
|---|---|---|
| 直接 `import` 参考项目的 `core/`，打进我们的 Agent 包 | 是（链接/同进程） | **Agent 整包必须 GPLv3**，且需分发源码 |
| 独立进程：Agent 只通过 HTTP/WS 与插件通信；插件不含其代码 | 否（at arm's length） | 插件可独立许可；Agent 仍 GPLv3 |
| 复制其代码片段/模板图片进我们的 MIT 仓库 | 是 | 不可行，必须 GPLv3 |

**建议**：
- `dsh-qq-farm`（插件半，宿主+面板）：**MIT**，不含任何派生代码；
- `dsh-qq-farm-agent`（Agent 半）：**GPLv3**，明确致谢上游；
- 模板资产（`templates/`）随 Agent 以 GPLv3 分发，不要混进插件包；
- 若你希望整个项目统一 GPLv3，也可以——只是会限制未来商用与部分用户的采用意愿。**这个点需要你拍板**（见 §13）。

### 11.2 合规提示

## 12. 关键设计决策记录（ADR 摘要）

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| A1 | 三层拆分（插件/协议/Agent） | 插件内直调 Python | 平台无关 + DSH 重启不中断 + 许可隔离 |
| A2 | 调度在 Agent 侧 | 调度在插件侧 | 长时任务不应依赖 GUI 会话存活 |
| A3 | REST 管命令、WS 管状态帧 | 全 WS / 全轮询 | 命令要幂等可鉴权；帧要可丢可合流 |
| A4 | M1 嵌入参考内核，不 fork 重写 | 自研内核 | 功能对等速度；代价是耦合，用 pin + 适配层控制 |
| A5 | 帧用 WebP/JPEG 单帧覆盖，不排队 | 视频流/MJPEG | 面板只要"最新一眼"，排队只会增加延迟 |
| A6 | 面板三级降级 | 只依赖 `conversation.view` | 内部契约会变，白屏不可接受 |
| A7 | 路由自建鉴权 | 复用 `/api` 栅栏 | `/plugins/**` 不在其保护范围（已核实） |

## 附录 A：FAP 错误码

| 码 | 语义 | 建议动作 |
|---|---|---|
| `E_NO_AGENT` | 连不上 Agent | 检查进程/地址/token |
| `E_WINDOW_LOST` | 窗口关闭或句柄失效 | 重启窗口（restart） |
| `E_WINDOW_SIZE` | 窗口尺寸/DPI 不符 | 调窗口（参考项目已有公式） |
| `E_CAPTURE_BLACK` | 连续截图无效 | 切前台截屏或修复重启 |
| `E_PAGE_UNKNOWN` | 页面识别失败超阈值 | 清弹窗 → 回主页 → 修复 |
| `E_STUCK` | 长时间无有效动作 | 修复 → 重启 → 停机通知 |
| `E_TEMPLATE_MISS` | 模板缺失/版本不匹配 | 更新模板包 |
| `E_TASK_DISABLED` | 任务被配置禁用 | 提示改配置 |
| `E_UNSUPPORTED` | 方法/字段不支持（版本不匹配） | 升级一侧 |
